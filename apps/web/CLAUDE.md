# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Next.js 16 (App Router, `src/` directory), React 19, TypeScript, Tailwind CSS 4 (via `@tailwindcss/postcss`), HeroUI v3 (`@heroui/react`, `@heroui/styles`; no provider, compound components, `onPress`). Import alias `@/*` maps to `src/*`.

`next.config.ts` enables `cacheComponents` and `partialPrefetching`.

Next.js here has breaking changes versus older versions: read the relevant guide in `node_modules/next/dist/docs/` before writing Next.js code (see `AGENTS.md`).

## Commands (from this directory, or use `--workspace=web` from the root)

```bash
npm run dev      # next dev, http://localhost:3000
npm run build    # next build (needs NODE_ENV=production or unset)
npm run start    # serve the production build
npm run lint     # ESLint (eslint-config-next + eslint-config-prettier)
npm run lint:fix
```

There is no test runner configured yet.

## Key files and routing

File-system routing under `src/app/`:

- `src/app/layout.tsx` - root layout
- `src/app/page.tsx` - `/` home, signed-in users only (client-side guard: no token redirects to `/login`): a header link to `/profile` with the avatar (or its placeholder) and the name (or the e-mail; `header-profile.tsx` loads `GET /users/me` each time the page is shown, so a saved name or avatar appears without signing in again, and falls back to the e-mail from the JWT when the load fails), meeting count, the 3 most recently created meetings from `GET /meetings` (owned and shared ones; each links to `/meetings/[id]`, a shared one carries a "Shared" chip, `shared-chip.tsx`), "Create meeting" and "Log out"; a `401` clears the token
- `src/app/login/page.tsx` - `/login` form (`POST /auth/login`), stores the token and redirects to `/`; links to `/register`; redirects away when already signed in
- `src/app/register/page.tsx` - `/register` form (`POST /auth/register`), stores the token and redirects to `/`; links to `/login`
- `src/app/profile/page.tsx` - `/profile`, signed-in users only (no token redirects to `/login`, content keyed by the token): loads `GET /users/me` (a `401` clears the token, other failures show Try again) and shows the avatar (`user-avatar.tsx`, shared with the home page header and the picker: the image cut to a circle, since HeroUI's fixed avatar radius squares off the large size, and a person icon when there is none, while it loads or when it fails to load), the name (or the e-mail when no name is set, `getDisplayName` in `src/app/profile.ts`, which also holds the `Profile` type and `getAvatarUrl`: the API answers a signed path relative to itself) and the e-mail, with Back (to `/`), Edit (to `/profile/edit`) and Change password (to `/profile/edit#change-password`, the form's id `CHANGE_PASSWORD_SECTION_ID` in `profile/constants.ts`)
- `src/app/profile/edit/page.tsx` - `/profile/edit`, signed-in users only (same redirect and token key): loads `GET /users/me` into the avatar picker and a name field (failures show Try again). The picker (`edit/avatar-picker.tsx`, `edit/use-avatar-upload.ts`) previews in a circle what Save keeps (the saved avatar, the picked image or the placeholder); a picked file is checked first (`edit/avatar-types.ts`: PNG / JPEG / WebP and 5 MB, the allow-list in `profile/constants.ts` mirrors `apps/api/src/users/avatar-types.ts`, keep both in sync; the reason shows under the picker and nothing is uploaded), then uploaded at once through tus (`POST /uploads` with `purpose=avatar`, one request, a progress bar). Picking another file, Remove or leaving the page terminates an upload in flight (one still being created once the server has answered); leaving also drops the picked image; a failed upload (`400` from the API's content check, e.g. a text file named `.png`) shows its reason and falls back to the saved avatar. Save while uploading asks to wait; Save sends `avatarUploadId` (the tus upload id) or `avatar: null` with the name, and a `404` / `409` for the upload resets the picker with a message. The page also checks the trimmed name against 50 characters (`profile/constants.ts`, mirrors the API's `UpdateProfileDto`), saves with `PATCH /users/me` (an empty name clears it; the API's `400` reason is shown under the field) and returns to `/profile`; Cancel goes back to `/profile`. Below it `edit/change-password-form.tsx` (card id `CHANGE_PASSWORD_SECTION_ID`; opened with that hash, it takes the focus instead of the name field): current, new and confirm password (`PasswordField` with `label` / `name`), checks a filled current password, the new one against the register limits and a matching confirmation, sends `POST /auth/password` (`403` shows "wrong current password" under the current field, the API's `400` reason goes under the new one), and on `204` empties the form and shows a success alert; the token stays, so the user stays signed in. The typed passwords are dropped when the page is left; a request in flight is not aborted (the server may already have changed the password), its answer shows on return
- `src/app/meetings/new/page.tsx` - `/meetings/new` form (`POST /meetings`), then back to `/`
- `src/app/meetings/[id]/page.tsx` - `/meetings/[id]` meeting page (params read inside a `Suspense` boundary, as Cache Components require); `meeting-view.tsx` loads `GET /meetings/:id` and `GET /meetings/:id/files` (`404` or a malformed id shows "Meeting not found", `401` clears the token). The meeting's `role` decides the page: the owner gets upload, delete and the participants section; a participant gets a read-only page ("Shared" chip, a note, files with Download only)
- `src/app/meetings/[id]/upload-area.tsx` - file picker and drag-and-drop, one row with a progress bar per file; `use-file-uploads.ts` uploads through the API's tus endpoint (`POST /uploads`, `tus-js-client`, 32 MB chunks, at most 3 uploads at a time, resume within the page session) and refreshes the file list on success. Cancel (queued, running or failed upload) removes the row and terminates the upload on the server (tus `DELETE /uploads/:id`, which removes the partial data); a network or server error shows Retry, which resumes from the server offset (`HEAD`) through a fresh `Upload` with `uploadUrl` (so automatic retries start over) without re-picking the file; `400` / `401` / `403` / `404` / `413` are final (only dismiss). An upload cancelled while it is being created keeps its slot until the creation answers and is then terminated; a `409` on cancel (the last chunk landed first) deletes the stored file. Focus moves to the row's Cancel after Retry and to the section heading after Cancel
- `src/app/meetings/[id]/file-types.ts` - client-side rejection (type allow-list and 2 GB limit, with the reason) before an upload starts; the allow-list in `meetings/[id]/constants.ts` mirrors `apps/api/src/meeting-files/file-types.ts`, keep both in sync
- `src/app/meetings/[id]/file-list.tsx` - completed files (name, type, a recording's duration, size, upload date, status chip with a spinner while `PROCESSING`, download); download asks `POST /meetings/:id/files/:fileId/link` for a short-lived signed URL (`files-api.ts` holds the link, download, retry and delete calls). A `FAILED` file shows its `failureReason` and, for the owner, Retry (`POST .../retry`; the answered file replaces the row and the list reloads, `409` / `404` reload it with a message; focus moves to the row's Download). A `READY` document or recording shows its summary (`file-preview.tsx` `FileSummary`, clamped to 4 lines; Show more appears only when the clamp hides text, measured with a `ResizeObserver`). Files the API marks `previewable` (PDF / PNG / JPEG) get Preview (`FilePreviewPanel`: `<img>` or an `<iframe>` of the signed URL with `&disposition=inline`, the iframe unless `navigator.pdfViewerEnabled === false`; an image that fails to load shows Try again; Open in a new tab opens the tab during the click and fills it with a link that is still valid); images also get a lazy thumbnail that asks for its link once the row nears the viewport and keeps the first image that loaded. Files the API marks `playable` (audio, video) get Play, which opens `RecordingPanel` (`recording-player.tsx`) under the row and starts playback: a native `<audio>` / `<video>` on the signed URL with `&disposition=inline` (the API serves byte ranges and keeps recording links valid for the duration plus 30 minutes). When loading fails (`MEDIA_ERR_NETWORK` / `MEDIA_ERR_SRC_NOT_SUPPORTED`, e.g. the link expired during a long session), the panel requests one fresh link and continues from the same position and play state; it does so again only after playback has moved `PLAYER_REFRESH_RESET_SECONDS` on, so a recording that fails at the same spot ends in an error instead of a refresh loop. A decode error, or a second failure, shows the reason with Try again (shared `PanelError` from `file-preview.tsx`): browsers report a failed request with the same code as an unknown format, so the panel asks the content URL for its status first (`probeFileLink`, body cancelled): served means the browser cannot play the format, `404` that the file is gone, anything else a load error. Under the player, once the recording is `READY`, the transcript from `GET /meetings/:id/files/:fileId` (`fetchTranscript`; the list leaves it out): one button per segment with its `m:ss` start, which seeks there and plays; the segment playing is highlighted (`aria-current`, accent bar; also right after the transcript loads while paused). The active index lives in a small external store the lines read with `useSyncExternalStore`, so during playback only the two lines whose highlight changes render, not the panel and a list of thousands of segments. The list scrolls itself, not the page, to keep it in view (instant with `prefers-reduced-motion`), except for `TRANSCRIPT_FOLLOW_PAUSE_MS` after the user scrolled or used it. A `FAILED` recording can still be played; its panel says there is no transcript. A video also gets the transcript as an English captions track (a WebVTT `data:` URL; `&`, `<` and `>` are escaped, since WebVTT reads them as tags and character references). On phones the panel has no frame and Chrome's mute button is hidden (`.recording-audio` in `globals.css`), so the native audio controls keep a usable timeline. A recording's summary is the same `FileSummary` as a document's; while it is `PROCESSING` the row says it is being transcribed (`PROCESSING_TEXT` in `constants.ts`). `useFileLink` reuses a link for 4 minutes measured with `performance.now()` (links live 5, the system clock does not matter) and drops it when a new request fails. Files that finish processing are announced in one `role="status"` region (emptied first, so a repeated message is read again); delete opens a HeroUI `AlertDialog` confirmation (Escape closes it unless the delete is pending) and calls `DELETE /meetings/:id/files/:fileId` (`404` counts as deleted); once the dialog has closed, `meeting-view.tsx` drops the file, reloads the list and moves focus to the Files heading. While any file is `PROCESSING`, `meeting-view.tsx` reloads `GET /meetings/:id/files` every 3 s (`PROCESSING_POLL_INTERVAL_MS`; one request at a time, no timer while the tab is hidden, one reload at once when it shows again); the list carries the summaries, and a `404` on reload shows "Meeting not found". `UPLOADING` files never come from the API: only the uploading owner sees them, as upload rows
- `src/app/meetings/[id]/participants-section.tsx` - owner only: participants from `GET /meetings/:id/participants` (a failed load shows Retry), add by e-mail once the list has loaded (`POST`, the API's reason for `400` / `404` / `409` shown under the field, success announced in a `role="status"` region) and remove after a HeroUI `AlertDialog` confirmation (`DELETE .../participants/:userId`; a missing participant counts as removed, a missing meeting is an error; the row goes once the dialog has closed and focus moves to the Participants heading). Calls in `participants-api.ts`. Both delete dialogs (files, participants) share `use-confirmed-removal.ts` (dialog state, pending / error, remove the row only after the dialog has closed, with a fallback timer) and `unmount-listener.tsx` (tells the hook the dialog has closed)
- `src/app/auth-storage.ts` - access token in `localStorage` (key `accessToken`) with a `useAccessToken()` hook (`undefined` while hydrating, then token or `null`; syncs across tabs), `getEmailFromToken`
- `src/app/api.ts` - `authorizedFetch(path, init)`: API call with the stored token; resolves to `null` without a token or on `401` (the token is cleared); `readErrorMessage(response)`: the API's error reason (a string or the first validation message)
- `src/app/password-field.tsx` - shared password input with show/hide toggle (`label` and `name` default to Password / `password`) and `getPasswordLengthError` (register and change password; counts code points like the API); `src/app/meetings.ts` - `Meeting` (with `role`: `owner` / `participant`) / `MeetingFile` (with `previewable`, `playable`, `durationMs`, `summary`) / `MeetingFileDetails` (plus `transcript`) / `Participant` types, date, file size and duration (`m:ss`, `h:mm:ss`) formatting
- `src/app/globals.css` - global styles: imports `tailwindcss` first, then `@heroui/styles`, plus the animated `.aurora` background, `.glass-card` styles and the phone-width `.recording-audio` controls
- `src/app/constants.ts` - API URL (`NEXT_PUBLIC_API_URL`, default `http://localhost:4000`), token key, email validation, theme storage key and the pre-hydration theme script; `src/app/register/constants.ts` - password limits (constants live in a `constants.ts` next to the component, not inline)
- `src/app/theme-toggle.tsx` - light/dark switch (`dark` class + `data-theme` on `<html>`, saved in `localStorage`; an inline script in `layout.tsx` applies it before hydration)
- `postcss.config.mjs` - PostCSS config with `@tailwindcss/postcss`
- `eslint.config.mjs` - flat ESLint config

## Per-user state

Next.js keeps a route's client state when the user leaves it (`cacheComponents`), so after logging out and in as someone else a page would show the previous user's data until its own loads. Signed-in pages therefore render their content in a child keyed by the token (`<HomeContent key={token}>`, `<ProfileContent key={token}>`, `<MeetingContent>` keyed by token and meeting id): another user or meeting gets a fresh tree. Do the same for new signed-in pages.

A side effect: right after leaving a form page (e.g. Save on `/profile/edit`), React Aria logs "If you do not provide a visible label, you must specify an aria-label…" from the hidden page's `TextField`. The fields do have visible labels; the warning comes from the kept, hidden tree and can be ignored.

## UI changes: mandatory visual check

For any change to the UI of this app:

- Always apply the `ui-ux-pro-max` skill.
- Always test the change visually through the Playwright MCP server (not any other browser tooling).
- The dev server is already running (http://localhost:3000); do not start it.
- The task is done only after the visual check has passed.
